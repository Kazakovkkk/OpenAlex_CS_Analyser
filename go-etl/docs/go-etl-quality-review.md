# ТЗ для Go-разработчика. Доведение Go-ETL до рабочего MVP

Реализуй шаги по порядку в директории `go-etl` на актуальной командной ветке, содержащей `ac6ebf5`. Применяй этот итоговый контракт по задачам 1–3 при расхождении с ранними ТЗ. Выполняй шаги самостоятельно, без промежуточного согласования проектных решений. При техническом препятствии выполни независимые шаги и зафиксируй конкретную причину остановки.

Go проверяет, нормализует и загружает данные OpenAlex в ClickHouse. Python управляет загрузкой через TUI, пересчитывает кэш и строит HTML-отчёт по задачам 2 и 3. Go-разработчик сдаёт код, инструкцию, Dockerfile и образ `go-etl`. Python-разработчик собирает общий Compose, лаунчеры и дистрибутив. VPS уже подготовлен. База `openalex` пуста, `load_phase` добавлен, TLS, роли и лимит `pipeline_writer=1` настроены. Разработчики выполняют текущую приёмку самостоятельно со своими учётными данными и коммитят свою часть в общий репозиторий.

## Шаг 1. Настрой рабочие режимы, роли и управление задачами

1. Проведи `etl serve --config PATH --addr :8081` и `etl ingest --config PATH --source s3` через один оркестратор. Используй общий рабочий `app.toml` для Go и Python. В репозитории это `py-analysis/config/app.toml`, в распакованном ZIP — `config/app.toml`. Compose монтирует его в Go как `/app/config/app.toml:ro` и передаёт `--config /app/config/app.toml`. Для прямого запуска из корня репозитория укажи `etl ingest --config py-analysis/config/app.toml --source s3`. Читай секции `[clickhouse]` и `[go_etl]`. Загружай пароли из указанных переменных окружения. Для VPS используй нативный TCP с TLS и проверкой сертификата. Отсутствующий рабочий конфиг должен давать ошибку запуска. Оставь `NoopSink` в явно выбранном сухом прогоне и в тестах.

   ```toml
   [clickhouse]
   host = "clickhouse"
   port = 9000
   database = "openalex"
   secure = false
   pipeline_writer_user = "pipeline_writer"

   [go_etl]
   base_url = "http://go-etl:8081"
   etl_writer_user = "etl_writer"
   etl_writer_password_env = "CLICKHOUSE_ETL_WRITER_PASSWORD"
   go_pipeline_writer_password_env = "CLICKHOUSE_GO_WRITER_PASSWORD"
   ```

2. В `cmd/etl/chsink.go` и `internal/clickhouse/client.go` замени открытие общего пула `pipeline_writer` при запуске на создание управляющей сессии по запросу. Открывай её только для перехода состояния, подтверждённой очистки или публикации. В пределах перехода выполняй все запросы через одно физическое соединение и закрывай его сразу после перехода. При обрыве открывай новую сессию и заново читай состояние перед повтором. При занятом слоте жди с паузами и возможностью остановки задания. Для неверных реквизитов и нехватки прав сразу возвращай соответствующую ошибку.
3. Под `etl_writer` вставляй `works` и `dim_topics`, читай индекс `work_id`, выполняй удаления и читай или записывай чекпоинты. Под Go-паролем `pipeline_writer` читай и публикуй `pipeline_state`, очищай `etl_checkpoints` и выполняй согласованную полную очистку. Python использует свой пароль того же логина. Настрой локальный ClickHouse 26.9 так, чтобы оба пароля делили один физический слот с `max_sessions_for_user=1`. Докажи ограничение открытием двух одновременных нативных сеансов.
4. Запускай **один экземпляр Go на целевую базу**. Перед ручным рабочим CLI останови HTTP-экземпляр для той же базы. В HTTP регистрируй задачи атомарно в `internal/jobs`. Объедини `ingest/start`, `ingest/restart` и рабочий `dimensions/sync` одним ограничением. На повтор обычного старта при активной загрузке верни `202` с ID этой загрузки. На повтор ранее принятого токена верни ту же задачу до проверки общего ограничения. Другую конкурирующую операцию отклони с `409 session_busy`. При shutdown сначала закрой приём новых задач записи, затем останови активную задачу и дождись её завершения.
5. Сохрани `--workers`, `--batch-size`, `--max-files`, `--max-records`, флаги диапазона и шардирования, включая `--shard=k/N`. Прогоны с лимитами, произвольной нижней границей S3 или отдельным шардом выполняй на изолированной тестовой цели либо через `NoopSink`. Они используют собственный журнал прогресса. Общий лимит `max_records` применяй к фактически отправленным строкам на уровне писателя. Для шардов определяй принадлежность файла по `file_index % shard_total` в исходном порядке манифеста. Штатный HTTP запускает один шард и публикует только полный срез.

**Результат шага.** Рабочие CLI и HTTP используют одну реализацию. Простаивающий сервис оставляет управляющий слот свободным. Нагрузочные и ограниченные прогоны изолированы от рабочего корпуса.

## Шаг 2. Собери воспроизводимый план загрузки

1. В `internal/app` загружай манифесты `works` и `topics` одного выпуска OpenAlex. Проверяй сущность, формат Parquet, дату, список и уникальность ключей файлов. Для работы с манифестами используй существующий S3-адаптер. Справочник Institutions оставь в диагностике. Обязательная загрузка Topics должна работать при недоступном манифесте Institutions.
2. Построй полный SHA-256 общего набора манифестов. Сериализуй через `json.Marshal` типизированный список манифестов с сущностью, форматом, датой и перечнем пар URL с `content_length`. Сортируй сущности по имени и копию списка файлов по URL. Сохраняй исходный порядок для шардинга. Используй один и тот же общий идентификатор для постановки задачи, возобновления, проверки перед публикацией и подтверждения перезапуска. Недоступный обязательный манифест возвращает `manifest_unavailable`.
3. При первой загрузке или подтверждённом полном перезапуске сформируй план всех файлов Works и Topics. Загружай публикации за все годы, прошедшие валидацию. Для инкремента выбери разделы Works с `updated_date` позже предыдущей опубликованной даты. При первом переходе со снимка 14.10.2026 включи также разделы за 14.10.2026. Для нового выпуска подготовь полное чтение Topics и обработку `deleted_ids.csv.gz`. Отсутствие новых файлов Works само по себе не завершает загрузку.
4. Сначала обработай незавершённое состояние `loading`. Из `idle` при обычной проверке уже опубликованного идентификатора верни существующую версию. При `force_reload=true` перечитай Topics из манифеста опубликованного выпуска. Для рабочего обновления справочника сохрани общий идентификатор выпуска, начни переход с фазой `incremental` и после успешной повторной записи повысь версию. При возобновлении этой операции бери идентификатор последнего `idle` из истории состояния. Когда он совпадает с целевым, продолжай план только по Topics с их чекпоинтами. При недоступности Topics именно этого выпуска верни ошибку и предложи штатную загрузку совместимого нового выпуска. Для пустого рабочего корпуса загружай Works и Topics вместе через обычный ingest.
5. При инкременте, в том числе при возобновлении, потоком считай из ClickHouse все существующие `work_id` и собери компактное множество `UInt64` на основе существующего Roaring64. Дождись полного чтения до обработки файлов. Для первого полного прохода начни с пустого множества. Обновляй его после подтверждённых вставок.

**Результат шага.** У задачи есть один идентификатор выпуска и списки обязательных файлов. Go повторно строит тот же план при возобновлении и умеет обновлять справочник независимо от наличия новых работ.

## Шаг 3. Нормализуй работы и темы

1. В `internal/normalizer` сделай один контракт валидации для S3 и ручного REST. Для новой работы основной области CS соответствует `primary_topic.field.id=17`. Пропускай отозванные и служебные работы, в том числе `is_xpac`. Принимай шесть типов `article`, `book-chapter`, `conference-paper`, `data-paper`, `software-paper`, `preprint`. Сначала проверь известный ID при инкременте, затем применяй окончательное решение по корпусу. Для ранее известной работы запиши пригодную обновлённую версию даже при смене типа, смене области или отзыве. При потерянной области используй `primary_field_id=0`. При потере обеих тематических привязок сохрани пустые массивы и `primary_topic_id=0`. Для служебной версии известной работы используй `primary_field_id=0`, чтобы исключить её после выбора актуальной строки.
2. Проверь положительный `work_id`, пригодный `updated_date`, тип и булевый `is_retracted`. Храни `source_updated_at` из источника в UTC. Для S3 допустимы годы от 1 до года снимка включительно. Для REST верхняя граница — текущий год UTC. Если `publication_year` отсутствует или равен `null`, восстанови его из пригодной `publication_date` в том же диапазоне. Структура JSON должна отличать отсутствующее поле и `null` от явно переданного нуля. Явно переданный некорректный год и расхождение с годом в пригодной дате приводят к отбраковке. При пригодном годе запиши непригодную или отсутствующую полную дату как `0`, а пригодную как `UInt32 YYYYMMDD`. Поддержи даты до 1900.
3. Сохрани тематические ID всех областей в порядке OpenAlex. Для повторяющегося `topic_id` оставляй первое вхождение вместе с его оценкой. Непригодную оценку записывай как `0`. Всегда сохраняй одинаковую длину `topic_ids` и `topic_scores`. При пригодном массиве тем `primary_topic_id` может быть нулём. Новую работу без пригодного массива и основного ID отбраковывай. Фильтр CS-тем и распределение тематического веса выполняет Python. Go сохраняет исходные оценки.
4. Записывай неизвестный источник публикации как `primary_source_id=0` и пустой тип. Различай известный FWCI со значением 0 и отсутствие пригодного значения через `has_fwci`. Наращивай `rejected_records` один раз на структурно отклонённую запись. Для валидного условия вне корпуса, отзыва, повтора и транспортной ошибки используй отдельные исходы. В журнале отдельно выводи число восстановленных годов.
5. В `internal/ingest/processor_s3.go` и `internal/sink/clickhouse.go` подключи Topics к обязательному рабочему пути. Пиши справочник всех областей в `dim_topics(topic_id, display_name, subfield_id, subfield_name)`. Проверяй допустимые ID и наличие принадлежности тем к направлениям. Сопоставь число считанных строк со значением `record_count`, когда оно дано для файла. Считай пустой обязательный итоговый справочник ошибкой загрузки.

**Результат шага.** Новые строки совместимы с DDL и Python. После `FINAL` изменение типа, области или отзыва известной работы корректно меняет её участие в отчёте.

## Шаг 4. Проведи запись, батчи и чекпоинты через одного писателя

1. В `internal/ingest` создай ограниченный канал порций. Воркеры скачивают, декодируют, валидируют и передают порции с указанием сущности, ключа файла и номера попытки. Передача по каналу передаёт владение буфером. Возвращай буфер в пул после обработки писателем. Воркеры сообщают об EOF или ошибке чтения. Все реальные вставки и чекпоинты выполняет одна горутина-писатель.
2. Писатель собирает отдельные батчи для Works и Topics. Для Works используй начальный `batch_size=10000`. Батч может включать строки нескольких файлов. Отправляй синхронные `INSERT` по заполнению батча и при окончании фазы. Пустой батч пропускай. EOF файла учитывай как условие его чекпоинта. Координатор закрывает входной канал после выхода всех воркеров и передаёт писателю итог задания. Писатель завершает запись остатка перед возвратом успешного результата.
3. После подтверждения ClickHouse увеличивай `written_records`, обновляй индекс известных ID и отмечай подтверждённые строки файла. Записывай `etl_checkpoints(entity, object_key, completed_at)`, когда файл дочитан до EOF и все принятые строки учтены подтверждённой вставкой или подтверждённым эквивалентом. При полностью отфильтрованном файле используй подтверждённый EOF. При сбое записи чекпоинта перечитай журнал. Если отметку подтвердить не удалось, заверши задачу ошибкой.
4. При повторе разрешай вставку эквивалентных строк, подтверждение которых потеряно. Для дедупликации работ в пределах задачи сопоставляй `work_id`, `source_updated_at` и содержимое строки. Добавляй в учёт только подтверждённые записи и увеличивай `dedup_dropped` только при фактическом пропуске. Сохраняй более новые версии того же `work_id`. При конфликтующем содержимом одного ID и одной версии прерви запись с ошибкой `corpus_incomplete`. Проверяй конфликты среди подтверждённых строк и внутри ещё не отправленного батча. Учитывай, что аналитика читает `ReplacingMergeTree(source_updated_at)` через `FINAL`.
5. При Stop прекрати выдачу файлов, отмени чтение источника и закрой канал после выхода воркеров. Заверши начатый `INSERT`, обработай уже переданные порции и отправь накопленный остаток. Выполни эти операции под отдельным контекстом завершения с общим пределом 60 секунд. Подтверждай только полностью дочитанные файлы. После выхода писателя верни `stopped`. При ошибке записи или истечении срока завершения верни `failed` с кодом причины. Если файл остался незавершённым, следующая попытка читает его с начала.
6. Повторяй временные ошибки чтения файла ограниченное число раз с паузой. После окончательного отказа обязательного файла прекращай загрузку. При ошибке писателя прекращай выдачу новой работы и разблокируй воркеры, ожидающие канал. Переходи к публикации после успешного завершения обеих фаз, подтверждения всех обязательных чекпоинтов и выполнения удалений.
7. После Works и Topics прочитай журнал удалений потоком. Отбери локальные ID по индексу и удаляй все версии этих работ пачками с ожиданием и проверкой результата. Показывай фазу обработки удалений в `current_item`. Повтори этот шаг при возобновлении, даже когда все файлы Works и Topics уже подтверждены.

**Результат шага.** Короткие файлы объединяются в крупные вставки Works. Потеря ответа на вставку не теряет строки. Stop отправляет хвост, а чекпоинты остаются точными.

## Шаг 5. Реализуй переходы и восстановление

В `internal/pipeline` используй столбец `load_phase` таблицы `pipeline_state`. Его контракт — `Enum8('none'=0,'resetting'=1,'full'=2,'incremental'=3)` с `DEFAULT 'none'`. Используй общую схему, уже применённую на VPS, и разверни её на тестовом ClickHouse. Читай и вставляй явный список столбцов. Каждый переход записывай одним синхронным INSERT полной строки с `state_revision+1`. Переноси аналитические поля из актуальной строки. Python переносит `load_phase` при публикации своей ревизии.

| Сценарий | Порядок действий |
| --- | --- |
| Новая загрузка из `idle` | Открой управляющую сессию, перечитай актуальную ревизию, очисти старый `etl_checkpoints`, запиши полную строку `loading` с фазой `full` или `incremental`, датой и общим хешем цели, `instance_id` и `job_id`. Подтверди переход, закрой сессию, запусти запись |
| Возобновление `full` или `incremental` | Убедись, что прежний процесс завершён и доступен закреплённый манифест. Под управляющей сессией запиши новую попытку с той же фазой, датой и хешем. Закрой сессию и продолжи по существующим чекпоинтам |
| Незавершённый снимок больше недоступен | Верни `snapshot_changed` только при подтверждённой смене выпуска. Выпусти токен на 30 минут, привязанный к ревизии, целевой базе, прежнему и новому общему идентификатору. Ожидай отдельного HTTP-подтверждения. Временную недоступность манифеста верни как `manifest_unavailable` |
| Подтверждённый перезапуск с нуля | Под управляющей сессией проверь токен, цель, ревизию и новый набор манифестов. Сначала синхронно зафиксируй `loading/resetting` с новой датой и общим хешем. Затем последовательно очисти `works`, `dim_topics` и `etl_checkpoints`. После подтверждения всех очисток запиши `loading/full`, закрой сессию и начни полный проход с начала |
| Восстановление `resetting` | Проверь закреплённую цель и остановку предыдущего процесса. Если цель доступна, повтори все три очистки под управляющей сессией и зафиксируй `loading/full`. Начни полную загрузку после подтверждения перехода. Если цель сменилась, пройди процедуру нового подтверждения. Сохрани кэш Python |
| Публикация | Повторно прочитай манифесты Works и Topics и сравни их общий хеш с планом. Под новой управляющей сессией перечитай состояние, сверь фазу, владельца, ожидаемую ревизию и манифест. Запиши полную строку `idle/none`. Для каждого нового успешно проверенного снимка обнови `snapshot_date`, `data_updated_at` и увеличь `data_version` ровно на 1, даже при отсутствии вставок и удалений |
| Потеря подтверждения публикации | Повторно прочитай состояние и проверь, зафиксирован ли ожидаемый переход для того же манифеста и владельца. Если зафиксирован, считай публикацию успешной. Если осталась ожидаемая строка `loading`, повтори переход после проверки. При другой ревизии установи фактический исход до любой повторной записи |

Между переходами рабочий писатель действует только при подтверждённом `load_state=loading`. Stop и отказ после этого перехода оставляют базу в `loading` с прежней опубликованной версией. Смена нового снимка или недоступная финальная сверка прерывают публикацию. Публикация новой версии сохраняет данные кэша и метаданные анализа прежней версии. Для уже опубликованного снимка обычная повторная проверка сохраняет версию и кэш.

**Результат шага.** После падения между очистками Go повторяет согласованный сброс. После падения во время записи Go продолжает тот же снимок. Python на протяжении обеих операций видит `loading`.

## Шаг 6. Закрой HTTP-контракт и изолируй REST OpenAlex

| Запрос | Действие |
| --- | --- |
| `GET /health` | Верни `200 {"status":"ok","instance_id":"…"}`. Назначай новый `instance_id` при каждом запуске процесса |
| `POST /api/v1/ingest/start` | Прими штатный JSON `{"source":"s3","shard_total":1,"shard_index":0}`. Верни `202` с `job_id`, `instance_id` и `state`. Повтор старта возвращает ID уже активной загрузки |
| `GET /api/v1/jobs/{job_id}` | Верни статус задачи или `404`. Используй состояния `running`, `completed`, `failed`, `stopped` |
| `POST /api/v1/jobs/{job_id}/stop` | Верни `200 {"stopped":true}` после принятия Stop и `stopped:false` для завершённой задачи. Итог определяет последующий GET. Подтверждённая публикация остаётся `completed` при позднем Stop |
| `POST /api/v1/ingest/restart` | Прими `{"restart_token":"…"}`. После принятия верни `202`. Повтор принятого токена в том же процессе возвращает ту же задачу. Просроченный, утративший силу или неизвестный токен возвращает `409 restart_offer_expired`. При смене условий после `202` передай этот код через статус задачи |
| `POST /api/v1/dimensions/sync` | Поддержи `force_reload` и общий протокол записи из шага 2 |
| `POST /api/v1/loadtest/start` | Пиши в выделенную нагрузочную таблицу `works_loadtest` |
| `POST /api/v1/openalex/request-key` | Прими явный запрос с email. Храни полученный ключ потоко-безопасно для следующей ручной API-задачи. Возвращай статус запроса и инструкции по активации. Значение ключа оставляй внутри Go |

В статусе задачи сохрани `job_id`, `kind`, `state`, `scanned_records`, `matched_records`, `written_records`, `dedup_dropped`, `rejected_records`, `bytes_read`, `http_requests`, `elapsed_sec`, `current_rps`, `current_item`, `avg_batch_ms`, `p50_batch_ms`, `p95_batch_ms`, `p99_batch_ms`, `error_code` и `error`. В HTTP-ошибках возвращай `code`, `message` и совместимое `error`. Для `snapshot_changed` передай дату незавершённого снимка в `previous_snapshot_date`, дату доступного снимка в `available_snapshot_date`, хост, порт и имя базы в `target_database` и токен в `restart_token`. Храни токены в памяти процесса Go. Исключи пароли, токены и ключи из журналов. Сохраняй причины `manifest_unavailable`, `disk_full`, `clickhouse_unavailable`, `session_busy`, `auth_failed`, `access_denied`, `corpus_incomplete` после прохождения через слои воркера и оркестратора.

REST-запуск выполняй только на выделенной цели в ручном режиме и в тестах. Сохрани явный выбор фильтра даты, диагностируй ограничения тарифа, считай HTTP-повторы, соблюдай `Retry-After` и общий предел 30 запросов/с на ключ. Поддержи ключ из `OPENALEX_API_KEY` и статус активации для ключа, полученного по явному запросу. Меняй исходный корпус только при штатной загрузке S3 или рабочей синхронизации его справочника.

**Результат шага.** Python управляет рабочей загрузкой по единому HTTP-контракту. Статусы различают Stop, частичную запись, отказ ClickHouse и необходимость подтверждённого перезапуска.
