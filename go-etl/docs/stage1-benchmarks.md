## 0. Дисклеймер о методике (важно для защиты)

### 0.1. Сравнивать форматы «по номеру файла» нельзя

`part_0071.parquet` и `part_0071.gz` внутри одной партиции `updated_date=2026-08-13`
содержат **разные статьи**:

| | parquet | jsonl.gz |
|---|---:|---:|
| строк | 176 609 | 176 609 |
| общих `work_id` | **27 524 (15.6%)** | |
| только в этом файле | 149 085 | 149 085 |
| CS-статей | 56 | 106 |
| CS только здесь | 49 | 99 (общих 7) |

Отсюда взялось «JSONL скачал 170% от Parquet» и «106 против 56» в первом прогоне.
Причина: писатели по-разному раскладывают записи дня по файлам. При этом
`record_count` **партиции** совпадает в обоих форматах у всех 396/396 партиций,
поэтому корректная единица сравнения — **партиция целиком** (в снапшоте есть
192 партиции из одного файла в каждом формате).

### 0.2. Формат: Parquet не «меньше», он «избирательнее»

По всему снапшоту `jsonl.gz` = **0.91×** от размера parquet (628.92 против 692.94 GiB).
На парных партициях: 0.91–1.02×. То есть выигрыш Parquet — **не сжатие**, а
projection pushdown (читаем 30–57% байт) и отсутствие gzip-CPU.

### 0.3. Сеть нестабильна, поэтому у стенда есть предохранитель

Дополнительно проверено на живом REST API (11.2026, без ключа): фильтр
`primary_topic.field.id:17` возвращает `meta.count = 12 074 740` работ; пагинация
курсором без ключа на второй странице даёт `401 {"error":"API key required for cursor
paging"}`, а `POST /api-keys` письмо отправляет, но **ключ в ответе не возвращает**
(приходит ссылка). Детали — в README, раздел «API-ключ OpenAlex».
Замеры на Дальнем Востоке/домашнем канале: 2 MiB Full GET занял 30.5 s в одном прогоне
и 0.74 s в другом. Поэтому в парный стенд добавлен замер базовой скорости
(1 MiB range GET) и переменная `BENCH_PART_MIN_MBPS`: если канал ниже порога,
стенд **отказывается писать цифры** (`SKIP`), а не портит медианы.

### 0.4. Ограничения REST API на бесплатном ключе (Метрика №7)

Проверено на живом API с бесплатным ключом (11.2026). Инкрементальная догрузка
«по дате обновления/создания», как она описана в ТЗ, **требует платного плана**:

| Запрос | Результат |
|---|---|
| `filter=primary_topic.field.id:17` | 200 OK |
| `filter=...,from_updated_date:2026-10-01` | **403 `Plan upgrade required`** (daily sync, Member+) |
| `filter=...,from_created_date:2026-10-01` | **403** (daily sync) |
| `filter=...,from_publication_date:2026-01-01` | 200 OK |
| `filter=...,publication_year:2026` | 200 OK |
| `sort=created_date:desc` / `sort=updated_date:desc` | **403** (daily sync) |

Поэтому в код добавлен **аддитивный** режим `date_filter_mode=publication`
(`from_publication_date`) — значения `updated`/`created` из контракта ТЗ остались, но на
бесплатном тире возвращают понятную ошибку `ErrPlanRequired` с подсказкой. Это нужно
согласовать с Python-разработчиком: контракт расширяется, а не ломается.

Замер реальной догрузки (500 записей, `publication`, `select` проекция полей):

| Метрика | Значение |
|---|---:|
| страниц / запросов / ретраев | 5 / 5 / 0 |
| записей просканировано / записано | 500 / 500 |
| трафик | **6 684 597 байт** (≈13.4 KB на запись) |
| расход квоты `meta.cost_usd` | **$0.0005** → **$0.10 на 100 000 записей** |
| время | 26.0 s (канал ~250 KB/s в момент замера) |

Повтор на 1000 записях подтвердил линейность: 10 страниц / 10 запросов,
**$0.001**, **12 393 885 байт** (12.4 KB на запись), 36.2 s, ретраев 0.

Экстраполяция для 12.07 млн CS-работ (столько их в снапшоте): **$12 и ~12 дней** при
лимите $1/день, либо ~4.5 ч при насыщении канала 5 MB/s — то есть API упирается в
**денежную квоту**, а не в сеть. S3-путь для тех же 12 млн работ качает 250–320 GiB
(~21–27 KB на работу) за ~17 ч и $0. Это и есть обоснование гибридной схемы из ТЗ:
S3 — основной источник, API — только свежие дельты.

Дополнительно: `select` (аналог projection pushdown для API) обязателен — полная запись
заметно тяжелее. Список допустимых полей API отдаёт в тексте ошибки на неизвестное поле;
`authors_count` в `select` **недопустим**, поэтому в JSON-ветке он считается как
`len(authorships)` (это уже было в нормализаторе).

## 1. Главный S3-бенчмарк (Метрика №3): JSONL.gz vs Parquet

### 1.1. Парные партиции (одни и те же статьи) — валидное сравнение

`BENCH_PART_RUNS=1`, канал ~5–6 MB/s. `written` совпадает во всех трёх режимах —
доказательство, что сравниваются одни и те же записи.

| Партиция | Записей | jsonl/pq | Режим | wall | Скачано | % от parquet | floor | % от floor | reqs | записей/с |
|---|---:|---:|---|---:|---:|---:|---:|---:|---:|---:|
| `2026-04-11` (4.96 MiB) | 7 110 | 1.02× | JSONL.gz | 1.48 s | 5.06 MiB | 102.0% | — | — | 1 | 4 811 |
| | | | Parquet Full GET | 1.94 s | 4.96 MiB | 100.0% | — | — | 1 | 3 667 |
| | | | **Parquet Range+prefetch** | 1.95 s | **2.37 MiB** | **47.7%** | 1.99 MiB | 118.8% | 25 | 3 641 |
| `2026-06-15` (50.58 MiB) | 26 019 | 0.91× | JSONL.gz | 6.83 s | 46.24 MiB | 91.4% | — | — | 1 | 3 809 |
| | | | Parquet Full GET | 8.14 s | 50.58 MiB | 100.0% | — | — | 1 | 3 195 |
| | | | **Parquet Range+prefetch** | **6.54 s** | **28.84 MiB** | **57.0%** | 28.47 MiB | **101.3%** | 25 | 3 976 |

Наблюдения:

* Range+prefetch скачивает **ровно проекцию** (101–119% от floor; превышение — проба футера 128 KiB и 4 байта magic) и на 50 MiB выигрывает и по времени, и по трафику.
* На 5 MiB малые файлы: 25 запросов дороже, чем 1 (RTT ~150–250 мс), поэтому время вровень, но трафик вдвое меньше.
* «Богатый» файл (26 тыс. записей на 50 MiB) даёт floor 57% — проекция экономит меньше, чем на «бедном» файле из 176 тыс. записей (floor 29.5%).

### 1.2. Full GET vs Range+prefetch по лестнице размеров (один файл)

`TestDiagPrefetchOnRealFiles`, канал ~5 MB/s, по одному прогону.

| Файл | Full GET | Range+prefetch | Трафик Range | % floor | reqs | bursts |
|---|---:|---:|---:|---:|---:|---:|
| 2.03 MiB | **0.74 s** / 2.03 MiB | 1.81 s | 1.04 MiB (51.1%) | 156.6% | 25 | 1 |
| 4.96 MiB | **1.54 s** / 4.96 MiB | 1.63 s | 2.37 MiB (47.7%) | 118.8% | 25 | 1 |
| 14.90 MiB | 4.94 s / 14.90 MiB | **3.16 s** | 8.02 MiB (53.8%) | 104.9% | 25 | 1 |
| 50.46 MiB | 12.03 s / 50.46 MiB | **5.52 s** | 15.22 MiB (30.2%) | 102.5% | 25 | 1 |
| 150.04 MiB | ~30 s (оценка) | **32.41 s** | 69.11 MiB (46.1%) | **100.5%** | 47 | 2 |
| 401.41 MiB | ~80 s (оценка) | **51.99 s** | 182.74 MiB (45.5%) | **100.3%** | 92 | 4 |

Вывод для порога `Full GET ↔ Range`: 2 MiB — однозначно Full GET; 5 MiB — ничья по
времени при вдвое меньшем трафике; с 15 MiB Range выигрывает и по времени.

**Порог оставлен настраиваемым, а не «зашитым»:** повторный свип 2/5/8/12/16 MiB на
текущем канале дал разброс в 40 раз на одном размере (5 MiB Full GET — 106 s,
12 MiB — 2.4 s), то есть измерялся не код, а сеть. Поэтому:
* библиотечный дефолт — 16 MiB (мелкие файлы за 1 запрос, крупные — префетч);
* в CLI есть флаг `etl ingest --full-get-threshold-mb N` — на канале VPS порог
  подбирается одним прогоном `TestDiagPrefetchOnRealFiles` и фиксируется флагом;
* в отчёте фиксируем **метод** и «хорошее окно» измерений (таблица выше), а не
  конкретное значение, зависящее от канала.

## 2. Итерации разгона Range-режима (для слайда «эволюция»)

Один и тот же файл `updated_date=2026-08-13/part_0071.parquet` (50.46 MiB, 176 609 строк).

| Конфигурация | wall | Скачано | % файла | reqs | Комментарий |
|---|---:|---:|---:|---:|---|
| Наивное окно 2 MiB, ретраи как было | **307.1 s** | 79.34 MiB | 157.3% | 41 | thrash + стойла по 30–60 s |
| Наивное окно 2 MiB + фикс ретраев | 46.4 s | 79.70 MiB | 158.0% | 54 | стойла убраны, трафик остался |
| Наивное окно 4 MiB | 63.7 s | 123.51 MiB | 244.8% | 47 | больше окно — хуже |
| Наивное окно 512 KiB | 21.2 s | 27.36 MiB | 54.2% | 67 | лучший из «наивных» |
| Без буфера (точные рейнджи) | 80.3 s | 15.03 MiB | 29.8% | 508 | трафик = floor, но 508 RTT |
| **Prefetch по футеру (64 MiB)** | **5.52 s** | **15.22 MiB** | **30.2%** | **25** | 102.5% от floor |

Почему 307 s: 79.34 MiB при ~5 MB/s — это ~16 s передачи; остальные ~290 s — стойла
(два слоя ретраев: 5 попыток SDK × 3 наших при `ResponseHeaderTimeout: 30s`).

### 2.1. Асинхронный бурст (устойчивость к «медленному» запросу)

Бурст префетча раньше был **синхронным**: `fillFrontier` ждал все 22 запроса, и один
медленный/перезапрошенный тормозил всё чтение (наблюдали 34 s вместо расчётных 17 s на
50 MiB при `retries=1`). Теперь:

* `ReadAt` ждёт **только то окно, которое реально нужно**;
* остальные окна бурста догружаются в фоновых горутинах;
* чтение из окна, которое ещё в полёте, ждёт его (через канал), не держа мьютекс;
* ошибка фоновой загрузки всплывает, когда это окно понадобится.

Инвариант «каждый нужный байт ровно один раз» сохранён: и на synthetic-файле
(`TestPrefetchWholeGroupDownloadsEachByteOnce`), и на реальных данных —
101.3% от floor на 50 MiB. Новые тесты: `TestPrefetchSlowBackgroundFetchDoesNotBlock`,
`TestPrefetchBackgroundErrorSurfaces`.

Трафик при этом не изменился (28.84 MiB на 50 MiB-партиции), меняется только
устойчивость к хвостам задержек; абсолютные секунды в таблицах выше получены на канале
~5–6 MB/s, повторный замер при 2.4 MB/s дал 28.2 s при том же трафике.

`go test -tags=inspect -run TestDiagPrefetchOnRealFiles -cpuprofile ...`:

* 27.2 s стенки из них **только 2.13 s CPU (7.8%)** — остальное сеть (канал ~2 MB/s);

| Стадия | Доля CPU |
|---|---:|

на входе и кандидат на оптимизацию Этапа 2 (чтение колоночных буферов напрямую).

## 6. Известные ограничения

1. **Сеть.** Абсолютные времена зависят от канала; сравнивать имеет смысл отношения (×) и `%` от floor, а не миллисекунды. За один вечер базовый канал менялся с 5.8 MB/s до 1.65 MB/s, а отдельные объекты S3 отдавались то за 0.7 s, то за 106 s — поэтому у парного стенда есть `BENCH_PART_MIN_MBPS`, который отказывается писать шум.
2. **`-race`** на текущей машине невозможен: `-race` требует cgo, а C-тулчейна нет (`CGO_ENABLED=0`). Прогнать `go test -race ./...` в WSL/на VPS перед сдачей.
3. **Оконный режим префетча** (row group не влезает в бюджет) на реальных файлах даёт 167–217% трафика — поэтому `DefaultPrefetchBudget = 64 MiB` покрывает целый row group OpenAlex (~55 MiB). Оконный режим оставлен как предохранитель.
4. **Пик RAM** растёт с префетчем: 50 MiB файл — 189–252 MiB heap (Full GET — 174 MiB). Меряется `HeapInuse` каждые 10 мс, то есть включает ещё не собранный мусор.
5. **Пиковая RAM и время** на 150/400 MiB Full GET не измерены (только оценка ~30 s и ~80 s по скорости канала).

### 4.3. Почему RoaringBitmap, а не `map[uint64]struct{}`

`go test -run '^$' -bench BenchmarkDedupMapVsRoaring -benchmem -benchtime 1x ./internal/normalizer`
на 1 000 000 реальных по распределению W-id:

| Структура | время на 1M вставок | выделено памяти | allocs |
|---|---:|---:|---:|
| `map[uint64]struct{}` | 126.7 ms | **37.8 MB** | 4 097 |
| `roaring64.Bitmap` | 153.9 ms | 7.6 MB | 99 884 |
| наш `WorkDeduplicator` (64 шарда) | **130.8 ms** | **6.98 MB** | 101 553 |

То есть по памяти выигрыш ≈5.4× на 1M id (для 12 млн IT-работ: ~84 MB против ~450 MB),
а по скорости вставки map выигрывает лишь ~3% — при этом он требует одного общего мьютекса
на 4 воркера (у нас 64 независимых шарда).

**Найденный при этом баг:** шардирование по младшим битам (`id & 63`) неверно для
roaring64: контейнеры ключуются старшими битами, поэтому каждый шард получал те же
~15 тысяч контейнеров с одним значением в каждом. Замеры до/после:

| Шардинг | время 1M вставок | выделено |
|---|---:|---:|
| `id & 63` (младшие биты) | 921.5 ms | **71.7 MB** |
| `(id >> 16) & 63` (старшие биты) | **130.8 ms** | **6.98 MB** |

Тест-страж: `TestDedupShardingKeepsContainersIntact` (память шардированной структуры не
должна превышать 1.2× от одного битмапа).
