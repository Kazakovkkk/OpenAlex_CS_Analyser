# План реализации ТЗ `go-etl-quality-review.md`

Документ — рабочий план Go-разработчика. Код по нему ещё не менялся.
База: ветка `main`, HEAD `ac6ebf5` («add Dockerfile, benchmark, sample generator, exact max_records budget, live rate»).
Рабочее дерево содержит незакоммиченные правки прошлого захода (6 изменённых файлов, 3 untracked) — они разбираются в шаге 0.

## 1. Цель и границы

Цель — выполнить шаги 1–7 нового ТЗ строго по его контракту и сдать:

1. рабочий Go-ETL с проверенным восстановлением после сбоев;
2. Docker-образ `go-etl` с фиксированным тегом и архив `docker image save`;
3. README с ручным ingest и воспроизводимыми командами приёмки;
4. результаты приёмки локально и на VPS;
5. полный выпуск Works + Topics, опубликованный на VPS, и сведения Python-разработчику (дата снимка, `data_version`, число работ и тем, освобождённый слот `pipeline_writer`).

Границы: Python-аналитика, TUI, Compose и дистрибутив — не наши. Инфраструктура VPS — только то, что требует ТЗ: схема с `load_phase`, лимит `max_sessions_for_user=1` на локальном стенде, применение схемы на VPS.
Замеры из старого ТЗ (§6.12–6.17) не блокируют приёмку по новому ТЗ; из них остаются только замеры, требуемые шагом 7.3.

### Шаг 1. Режимы, роли и управление задачами

#### 1.1 Конфиг и два режима работы
- Сделать `--config` обязательным для `serve`, `ingest`, `sync-dims`; отсутствие/нечитаемость рабочего конфига — ошибка запуска, а не тихий `NoopSink`.
- Ввести явный `--dry-run` (и `--checkpoint-dir` только для диагностики): `NoopSink` используется только при явном сухом прогоне и в тестах. В тестах `App` собирается с `NoopSink` напрямую.
- Читать только `[clickhouse]` и `[go_etl]`; пароли — из env по `*_password_env`; TLS с проверкой сертификата; в логах только имена переменных/`<redacted>`.
- Поддержать оба пути: `etl ingest --config py-analysis/config/app.toml --source s3` (в репозитории Python) и `--config config/app.toml` (в ZIP); для локальной работы — `config/app.local.toml`.
- Тесты: отсутствие файла, битый TOML, пустой хост, отсутствие env-пароля, `--dry-run` без конфига.

#### 1.2 Управляющая сессия `pipeline_writer`
- `internal/clickhouse/client.go`: вынести `buildOptions` и добавить `OpenSQL` (`ch.OpenDB`, `MaxOpenConns=1`, `MaxIdleConns=1`) для `database/sql`-пула управляющего пользователя.
- Новые `internal/pipeline/conn.go` (интерфейс `ExecContext/QueryContext/QueryRowContext`) и `internal/pipeline/slot.go`:
  - `Slot.Run(ctx, fn)` открывает `db.Conn(ctx)` (физический слот), выполняет переход целиком, закрывает соединение сразу;
  - занятый слот (`session_busy`) — пауза с backoff и выходом по `ctx.Done()`, ограниченное число попыток;
  - обрыв соединения посреди перехода — новая сессия и повтор `fn` с обязательным перечитыванием состояния;
  - `auth_failed`/`access_denied` — сразу ошибка без ретраев.
- `internal/pipeline/state.go`, `checkpoint.go`, новый `reset.go`: все переходы и согласованные очистки — через `Slot`; мьютекс процесса убрать (сериализует слот).
- `cmd/etl/chsink.go`: `pipeline_writer` больше не открывается на старте; `etl_writer` остаётся пулом для works/dim_topics/индекса/удалений/чекпоинтов.
- Тесты без ClickHouse: фейковый `Conn`, N `session_busy` → ровно N повторов; обрыв → `fn` вызван заново; отмена → выход; auth → без ретрая.

#### 1.3 Роли и лимит `max_sessions_for_user=1`
- Проверить и при необходимости поправить гранты: `etl_writer` — `INSERT works/dim_topics`, `SELECT work_id`, `ALTER DELETE works`, `SELECT/INSERT etl_checkpoints`; `pipeline_writer` — `SELECT/INSERT pipeline_state`, `TRUNCATE etl_checkpoints/works/dim_topics`; под `pipeline_writer` нельзя писать `works`.
- Локальный ClickHouse 26.9: найти рабочую конфигурацию лимита для двух SQL-пользователей с одним логином и разными паролями (профиль в `local/conf/users.d` и/или `SETTINGS`), применить, **доказать** открытием двух одновременных нативных сеансов: второй получает отказ, классифицируемый как `session_busy`. Integration-тест должен утверждать отказ, а не делать `Skip`.
- Зафиксировать exact-настройку в README/`docs/vps-checklist.md`, чтобы инфраструктура повторила её на VPS.
- Evidence: команда/лог двух сеансов в `docs/`.

#### 1.4 Единый оркестратор и write-slot
- `internal/jobs`: атомарная регистрация «проверка лимита + дедупликация + создание задачи» под одним lock. Отдельный write-slot для `ingest/start`, `ingest/restart`, `dimensions/sync`; `loadtest` сюда не входит.
- Повтор обычного старта при активной загрузке — `202` с ID этой загрузки (фактический `state`, не всегда `running`).
- Реестр принятых restart-токенов `token → job_id`: повтор токена возвращает ту же задачу **до** проверки общего лимита.
- Конкурирующая операция — `409` с телом `{code:"session_busy", message, error}`.
- Shutdown: сначала закрыть приём новых задач записи (drain-гейт в HTTP), затем остановить активную задачу и дождаться её завершения; отдельный контекст 60 с.
- Простаивающий `serve` не держит управляющий слот и не мешает Python забрать слот.
- Тесты: два параллельных `ingest/start` → один job; повтор токена; конкурент `dimensions/sync` → 409; shutdown при активной задаче; после завершения задачи новые запросы снова принимаются.

#### 1.5 Флаги, лимиты и изоляция
- Сохранить `--workers`, `--batch-size`, `--max-files`, `--max-records`, диапазон даты, `--shard-index/--shard-total`, `--shard=k/N`.
- Диагностический прогон = `--dry-run`, `--max-files`, `--max-records`, `--from-date` (S3), отдельный шард или `--source api`: собственный журнал прогресса (отдельный файл/префикс с параметрами), никаких записей в `pipeline_state`/`etl_checkpoints`, запись только в `NoopSink` или выделенную тестовую цель.
- Штатный HTTP: один шард (`shard_total=1`, `shard_index=0`) — сервер форсирует/валидирует, иначе `400`; публикуется только полный срез.
- `max_records` — жёсткий лимит на уровне писателя по фактически отправленным/подтверждённым строкам; при обрезке бюджет не теряется.
- Шардинг — `file_index % shard_total` в исходном порядке манифеста (до любой сортировки).
- Убрать публикацию усечённого корпуса: `--from-date` не должен приводить к `Publish`.

**DoD шага 1:** рабочие CLI и HTTP идут через один `app`/оркестратор; простой `serve` не занимает слот; лимиты изолированы; есть тесты на 202/409/shutdown.

### Шаг 2. Воспроизводимый план загрузки

#### 2.1 Манифесты Works и Topics одного выпуска
- Новый загрузчик в `internal/app` (файл `release.go`): манифесты Works и Topics одного выпуска через существующий S3-адаптер; Institutions — только диагностика, его 404/5xx не блокирует Topics.
- Валидация каждого манифеста (`internal/adapters/s3/manifest.go`): сущность соответствует (works/topics), `format = parquet`, дата `YYYY-MM-DD`, непустой список файлов, URL разбирается, ключи файлов уникальны (URL и object key), `content_length`/`record_count` не отрицательны.
- Типизированные ошибки `ErrManifestUnavailable` (404/5xx/сеть) и `ErrManifestInvalid`; маппинг в `error_code=manifest_unavailable`.

#### 2.2 Единый Release ID
- Ввести `Release` (сущность, формат, дата, файлы `{url, content_length}`) и `Release.ID()`:
  - сформировать типизированный список манифестов;
  - сущности отсортировать по имени; копию списка файлов — по URL;
  - сериализовать через `json.Marshal` и взять SHA-256;
  - исходный порядок файлов сохранить для шардинга.
- Один Release ID используется везде: постановка задачи, `loading_manifest_id`, возобновление, проверка перед публикацией, подтверждение перезапуска, `dimensions/sync`.
- Убрать works-only fallback и разные формулы (`CombineIDs`, topics-only ID).
- Тесты: golden SHA, независимость от порядка входного JSON, уникальность при изменении даты/файла/`content_length`, 404 → `manifest_unavailable`.

#### 2.3 Построение плана

- Первая загрузка и подтверждённый полный перезапуск — план всех файлов Works и Topics. Публикации за все годы, прошедшие валидацию (год партиции ≥ 1 и ≤ год снимка).

#### 2.4 Состояние до плана и особые ветки

  - незавершённый `loading` обрабатывать первым (resume или смена снимка);
  - из `idle` при обычной проверке уже опубликованного Release ID вернуть существующую версию без записи;
  - `force_reload=true` — перечитать Topics из манифеста опубликованного выпуска (если release ID не совпал/манифест недоступен — `manifest_unavailable` с предложением штатной загрузки совместимого нового выпуска);
  - рабочее обновление справочника: сохранить общий Release ID, начать переход с фазой `incremental`, после успешной перезаписи повысить `data_version`;
  - при возобновлении брать ID последнего `idle` из истории состояния; если он совпадает с целевым — продолжать только Topics с их чекпоинтами;
  - пустой рабочий корпус — обычный ingest Works+Topics вместе.

#### 2.5 Индекс известных `work_id`
- При инкременте (включая resume) всегда строить индекс: потоком читать все `work_id` из ClickHouse в компактное множество `UInt64` на базе существующего Roaring64; дождаться полного чтения до обработки файлов.
- Первый полный проход начинается с пустого множества.
- Обновлять индекс после подтверждённых вставок (hook писателя из шага 4).
- Тесты: блокирующий фейковый `Conn` доказывает чтение до старта обработки; пустой индекс; Add после ack; resume.

**DoD шага 2:** у задачи один Release ID и полные списки обязательных файлов; Go детерминированно повторяет план при возобновлении; словарь обновляется без новых работ.

### Шаг 3. Нормализация работ и тем

#### 3.1 Один контракт для S3 и REST
- `internal/normalizer`: единая функция решения (parse → known ID при инкременте → структурная валидация → решение по корпусу), общая для Parquet и JSON.
- Корпус: `primary_topic.field.id=17`; шесть типов (`article`, `book-chapter`, `conference-paper`, `data-paper`, `software-paper`, `preprint`); отозванные (`is_retracted=true`) и служебные (`is_xpac`) не добавляются как новые.
- Гейт корпуса перенести **после** проверки известного ID (сейчас он в reader до Append — `internal/adapters/s3/parquet_reader.go:250`): известная работа записывается пригодной обновлённой версией даже при смене типа, области или отзыве.
- Семантика известной работы: потеряна область — `primary_field_id=0`; потеряны обе тематические привязки — пустые массивы и `primary_topic_id=0`; служебная версия известной работы (xpac/отзыв) — `primary_field_id=0`, чтобы `FINAL`-выбор актуальной строки исключил её из анализа.
- Новая работа без пригодного массива тем и без основного ID — отбраковка.

#### 3.2 Год и дата
- Presence-aware JSON-модель: `publication_year *int32`, `publication_date *string` (nil = отсутствие/`null`); явный `0`/отрицательный год — отбраковка, а не восстановление.
- Проверять `work_id > 0`, пригодный `updated_date`, тип, булевый `is_retracted`; `source_updated_at` — UTC.
- Годы: S3 — 1..год снимка; REST — до текущего года UTC. Год отсутствует/`null` — восстановить из пригодной `publication_date` в том же диапазоне; расхождение года и даты — отбраковка.
- Пригодный год + непригодная/отсутствующая полная дата → `publication_date=0`; пригодная → `UInt32 YYYYMMDD`; даты до 1900 поддерживаются (проверить границы парсеров).
- В журнале — число восстановленных годов.

#### 3.3 Темы
- Все тематические ID в порядке OpenAlex; дубликат `topic_id` — первое вхождение с его оценкой; непригодная оценка — `0`; длины `topic_ids`/`topic_scores` всегда равны.
- При пригодном массиве тем `primary_topic_id` может быть `0`.
- Go сохраняет исходные оценки; фильтр CS-тем и распределение веса — Python.

#### 3.4 Источник, FWCI, счётчики, исходы
- Неизвестный источник — `primary_source_id=0` и пустой тип.
- `has_fwci` различает известный `0` и отсутствие/непригодное значение.
- `rejected_records` — ровно один раз на структурно отклонённую запись; отдельные исходы для валидной записи вне корпуса, отзыва, повтора, транспортной ошибки.
- Повторный проход файла не должен повторно накручивать `rejected_records`.

#### 3.5 Topics на обязательном рабочем пути
- `internal/ingest/processor_s3.go` и `internal/sink/clickhouse.go`: Topics читаются и пишутся в том же рабочем прогоне, что Works; `dim_topics(topic_id, display_name, subfield_id, subfield_name)`.
- Валидация справочника: `topic_id > 0`, допустимые `subfield_id`, принадлежность темы направлению (field/subfield), без молчаливого clamp.
- Сверка числа считанных строк с `record_count` файла, когда он задан.
- Пустой обязательный итоговый справочник — ошибка загрузки.

**DoD шага 3:** новые строки совместимы с DDL и Python; после `FINAL` смена типа/области/отзыва корректно меняет участие работы в отчёте; табличные тесты на каждый сценарий.

### Шаг 4. Запись, батчи и чекпоинты через одного писателя

#### 4.1 Канал порций и воркеры
- Новый `internal/ingest/portion.go`: порция = `{entity, object_key, attempt, rows, eof, err}`; передача по каналу передаёт владение буфером; после обработки писателем буфер возвращается в пул.
- Воркеры: скачивают файл, декодируют, валидируют и отправляют порции; сообщают EOF или ошибку чтения; сами не вставляют и не ставят чекпоинты.
- `internal/ingest/coordinator.go`: ограниченный канал, закрытие после выхода воркеров, передача писателю итога задания.

#### 4.2 Один писатель
- Новая горутина-писатель: отдельные аккумуляторы Works и Topics; Works `batch_size=10000` по умолчанию; батч может смешивать строки нескольких файлов.
- Синхронный `INSERT` по заполнению батча и в конце фазы; пустой батч пропускается; остаток дописывается до успешного возврата.
- `internal/sink` остаётся только исполнителем INSERT; чтение/нормализация из sink не вызываются.

#### 4.3 Чекпоинты
- После подтверждения ClickHouse: `written_records++`, обновление known-id индекса, отметка подтверждённых строк файла.
- `etl_checkpoints(entity, object_key, completed_at)` — когда файл дочитан до EOF и все принятые строки учтены подтверждённой вставкой или подтверждённым эквивалентом; полностью отфильтрованный файл — подтверждённый EOF.
- При сбое записи чекпоинта — перечитать журнал; если отметку подтвердить нельзя, задача завершается ошибкой (не «успех с потерей»).

#### 4.4 Дедупликация и конфликты
- В пределах задачи ключ — `(work_id, source_updated_at)` + содержимое строки; более новые версии одного `work_id` сохраняются.
- В учёт идут только подтверждённые записи; `dedup_dropped` увеличивается только при фактическом пропуске.
- Конфликтующее содержимое одного ID и одной версии — `corpus_incomplete`; проверять и подтверждённые строки, и ещё не отправленный батч.
- Повтор файла после потери ответа на INSERT разрешён: эквивалентные строки не считаются ошибкой и не искажают `written_records`.
- Помнить, что аналитика читает `ReplacingMergeTree(source_updated_at)` через `FINAL`.

#### 4.5 Stop
- Stop: прекратить выдачу файлов, отменить чтение источника, закрыть канал после выхода воркеров.
- Писатель завершает начатый INSERT, обрабатывает уже переданные порции и отправляет накопленный остаток под отдельным контекстом завершения с общим пределом 60 с.
- Подтверждать только полностью дочитанные файлы; после выхода писателя — `stopped`; ошибка записи/таймаут — `failed` с кодом причины.
- Незавершённый файл следующая попытка читает с начала.

#### 4.6 Ошибки и публикация
- Ограниченные повторы временных ошибок чтения с паузой; окончательный отказ обязательного файла прекращает загрузку.
- Ошибка писателя прекращает выдачу новых файлов и разблокирует воркеров.
- Публикация — только после успешного завершения Works и Topics, подтверждения всех обязательных чекпоинтов и выполнения удалений.

#### 4.7 Удаления
- После Works и Topics — потоком `deleted_ids`; отбор локальных ID по индексу; удаление всех версий пачками с ожиданием и проверкой результата; фаза в `current_item`.
- Повторять шаг при возобновлении, даже если все файлы Works/Topics уже подтверждены.

**DoD шага 4:** короткие файлы объединяются в крупные вставки; потеря ответа на INSERT не теряет строки; Stop отправляет хвост; чекпоинты точные; удаления не пропускаются.

### Шаг 5. Переходы и восстановление

#### 5.1 Схема и базовые правила
- `schema.sql`: `load_phase Enum8('none'=0,'resetting'=1,'full'=2,'incremental'=3) DEFAULT 'none'`; применить на локальном стенде и VPS (согласовано с уже применённой схемой VPS).
- Чтение/вставка — только явный список колонок; каждый переход — один синхронный `INSERT` полной строки с `state_revision+1`; аналитические поля переносятся из актуальной строки; Python переносит `load_phase` при своей публикации (контракт фиксируем в README).

#### 5.2 Сценарии (ровно по таблице ТЗ)
1. **Новая загрузка из `idle`:** управляющая сессия, перечитать ревизию, очистить старый `etl_checkpoints`, записать `loading` с фазой `full|incremental`, датой и Release ID, `instance_id`, `job_id`; подтвердить, закрыть сессию, начать запись.
2. **Возобновление `full|incremental`:** убедиться, что прежний процесс завершён, а закреплённый манифест доступен; записать новую попытку с той же фазой/датой/хешем; продолжить по чекпоинтам.
3. **Снимок недоступен:** `snapshot_changed` только при подтверждённой смене выпуска; токен 30 минут, привязка к ревизии, целевой базе, предыдущему и новому Release ID (и датам); ожидать отдельного HTTP-подтверждения; временную недоступность манифеста вернуть как `manifest_unavailable`.
4. **Подтверждённый перезапуск:** под сессией проверить токен, цель, ревизию, новый набор манифестов; синхронно записать `loading/resetting` с новой датой/хешем; последовательно очистить `works`, `dim_topics`, `etl_checkpoints` с подтверждением каждой очистки; записать `loading/full`, закрыть сессию, начать полный проход.
5. **Восстановление `resetting`:** проверить закреплённую цель и остановку прежнего процесса; если цель доступна — повторить все три очистки и записать `loading/full`; если цель сменилась — новое подтверждение; кэш Python сохранить.
6. **Публикация:** повторно прочитать манифесты Works и Topics, сравнить общий хеш с планом; под новой сессией перечитать состояние, сверить фазу/владельца/ожидаемую ревизию/манифест; записать `idle/none`. Для каждого нового успешно проверенного снимка обновить `snapshot_date`, `data_updated_at` и увеличить `data_version` ровно на 1, даже без вставок и удалений.
7. **Потеря подтверждения публикации:** перечитать состояние и проверить, зафиксирован ли ожидаемый переход для того же манифеста/владельца; если да — успех; если осталась ожидаемая `loading` — повторить после проверки; при другой ревизии — установить фактический исход до повторной записи.

#### 5.3 Правила эксплуатации
- Между переходами рабочий писатель действует только при подтверждённом `load_state=loading`.
- Stop/отказ после перехода оставляют базу в `loading` с прежней опубликованной версией.
- Смена снимка или недоступная финальная сверка прерывают публикацию.
- Публикация новой версии сохраняет кэш и метаданные анализа (`analysis_*`) прежней версии.
- Для уже опубликованного снимка обычная проверка сохраняет версию и кэш.

#### 5.4 Тесты
- Фейковый `Conn` с таблицей сценариев: все 7 строк, падение после каждой из трёх очисток, падение между `resetting` и `full`, потеря ответа на INSERT состояния, публикация без вставок, повторная публикация того же снимка, токен: TTL/ревизия/цель/два ID/одноразовость.
- Интеграционные на ClickHouse: `store_integration_test.go` на `OpenSQL`, фазы и повторные попытки.

**DoD шага 5:** после падения между очистками Go повторяет согласованный сброс; после падения во время записи продолжает тот же снимок; Python на протяжении операций видит `loading`; публикация идемпотентна.

### Шаг 6. HTTP-контракт и изоляция REST

#### 6.1 Эндпоинты и состояния
- `GET /health` → `200 {"status":"ok","instance_id":…}`; новый `instance_id` на запуск.
- `POST /api/v1/ingest/start` — штатный JSON `{source:"s3",shard_total:1,shard_index:0}`; `202` с `job_id`, `instance_id`, фактическим `state`; повтор — ID активной загрузки; HTTP принимает только один шард (иначе `400`).
- `GET /api/v1/jobs/{job_id}` — статус или `404`; состояния `running/completed/failed/stopped`.
- `POST /api/v1/jobs/{job_id}/stop` — `200 {"stopped":true}` после принятия, `false` для завершённой; подтверждённая публикация при позднем Stop остаётся `completed`.
- `POST /api/v1/ingest/restart` — `{restart_token}`; после принятия `202`; повтор принятого токена в процессе — та же задача; просроченный/неизвестный/утративший силу — `409 restart_offer_expired`; смена условий после `202` — код через статус задачи.
- `POST /api/v1/dimensions/sync` — `force_reload` и общий write-slot/протокол шага 2.
- `POST /api/v1/loadtest/start` — выделенная `works_loadtest`.
- `POST /api/v1/openalex/request-key` — явный email; потокобезопасное хранение ключа для следующей ручной API-задачи; ответ со статусом/инструкцией активации; значение ключа не возвращается и не логируется.

#### 6.2 Статус и ошибки
- В статусе: `job_id`, `kind`, `state`, `scanned_records`, `matched_records`, `written_records`, `dedup_dropped`, `rejected_records`, `bytes_read`, `http_requests`, `elapsed_sec`, `current_rps`, `current_item`, `avg_batch_ms`, `p50_batch_ms`, `p95_batch_ms`, `p99_batch_ms`, `error_code`, `error`.

- Токены — только в памяти Go; исключить пароли/токены/ключи из логов и статусов.

#### 6.3 REST и нагрузка
- REST-запуск — только выделенная цель, ручной режим и тесты: HTTP принимает только `source=s3`; `etl ingest --source api` остаётся ручным CLI-режимом.

## 6. Тестовая стратегия

- Юнит-тесты на каждый пункт ТЗ; табличные кейсы для нормализатора, плана, переходов, слотов и HTTP.
- Тесты без сети/ClickHouse: фейковые `Conn`, `ManifestSource`, `Sink`, HTTP-клиент.
- Интеграционные (`-tags=integration`, `-p 1`): живой ClickHouse, фикстура выпуска, потеря подтверждения, Stop, очистки, публикация.
- `go test ./...` и `go vet ./...` — на каждом коммите; `go test -race ./...` — на вехах M4/M5/M7 и перед сдачей (нужен gcc/Linux, см. риски).
- Не ослаблять тесты: `Skip` при недоступном ClickHouse допустим только для локального окружения, но приёмочные сценарии должны иметь возможность падать; запрещено «зеленить» приёмку отключением проверок.

## 7. Риски и внешние зависимости

| Риск | Влияние | Что делаем |
|---|---|---|
| Нет Docker-демона на машине | Нельзя поднять локальный ClickHouse 26.9 для шагов 1.3, 5, 7.2 | Просим запустить Docker Desktop; до этого разрабатываем на фейках, интеграцию откладываем до M5 |
| `-race` требует cgo/gcc, в окружении `CGO_ENABLED=0` и gcc нет | Блокирует 7.1 и финальный `go test -race ./...` | WSL/Linux/CI или установка gcc; альтернатива — Docker-образ `golang` (нужен Docker) |
| Пароли VPS получены в чате | Секреты уже раскрыты в переписке | Используем только через env, в файлы/логи не пишем; после сдачи — перевыпустить все пароли (отметить в README/передаче) |
| Лимит `max_sessions_for_user=1` на VPS работает (доказано), на локальном 26.9 ранее «не работал» | Риск не воспроизвести 1.3 локально | В первые дни M1 настраиваем локальный стенд по образцу VPS (SQL-пользователи, профиль/квота) и доказываем двумя сеансами; настройку фиксируем в README |
| Ротация публичного S3-релиза во время загрузки | `snapshot_changed`/повтор | Release ID + токен подтверждённого перезапуска; VPS-прогон запускаем сразу после проверки релиза |
| Долгий полный прогон (~12,6 млн работ) | Время/диск/сеть | Запускаем как отдельную операцию, следим за `disk_full`, повторяем по чекпоинтам |
| Общий `py-analysis/config/app.toml` отсутствует в этом репозитории | Нечего монтировать в Compose | Для локальной проверки используем `config/app.local.toml`; Python-разработчику передаём требуемый контракт секций и путь |
| Грязное дерево/непрокоммиченные правки | Не воспроизводится приёмка | Шаг 0: чистка, коммиты по вехам |

## 8. Правила выполнения

1. Строго новый контракт; при расхождении со старым ТЗ действует `go-etl-quality-review.md` (п. 3 преамбулы).
2. Шаги выполняются по порядку; каждый шаг заканчивается тестами, `go vet`, обновлением README/доков и коммитом.
3. Пароли/токены/ключи — только из env/памяти; в логи не попадают.
4. Ограниченные/диагностические прогоны не меняют рабочий корпус и `pipeline_state`.
5. Не «подгонять» приёмку: каждая строка таблицы ТЗ имеет тест или воспроизводимую команду с evidence.
6. Все временные программы/фикстуры — в `tmp/`/`testdata` и не попадают в образ/дистрибутив.
7. Пуш в общий репозиторий — после подтверждения; до этого коммиты локальные, чтобы не ломать общую ветку.
